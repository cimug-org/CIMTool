cimtool-cli: Generating Artifacts Outside the Workbench

cimtool-cli (cimtool-cli.jar) is a companion command-line tool that generates a project's artifacts outside the CIMTool workbench. It runs the same builders that CIMTool runs when you save a profile, so a profile built on the command line produces the same XSD, JSON Schema, RDFS, OWL, AsciiDoc, PlantUML and other artifacts as one saved in the Profile Editor. It needs no workbench and no display, so it can run in a script, on a server or in a continuous-integration pipeline.

This page describes what the tool is for and how it fits with your CIMTool projects. For its command-line options, usage examples, exit codes and logging, see Using CIMTool in CI/CD Pipelines with cimtool-cli on cimtool.ucaiug.io.

What It Is For: SchemaOps

cimtool-cli supports a SchemaOps way of working: treating your CIM schema and profiles as versioned source, kept in a repository such as Git, and regenerating everything derived from them automatically, in the way DevOps treats application source code. For example, a pipeline can:

  • regenerate every profile's artifacts each time a change to a CIMTool project is committed or proposed in a pull request;
  • pass the generated AsciiDoc documentation to the Asciidoctor command-line tools to build a finished HTML or PDF document, and publish it;
  • generate LinkML from the profiles and pass it on to LinkML's own tools to produce code, documentation or further artifacts.

It runs on Windows, Linux and macOS, so it can be used with any continuous-integration system, such as GitHub Actions, GitLab CI, Jenkins or Azure Pipelines, and in containers. The CIMTool workbench itself is released for Windows only.

How It Works with Your Projects

cimtool-cli works on a CIMTool project folder: the folder that holds the project's Schema, Profiles and other folders (see Project Explorer and Project Folders). You create and edit the project in the workbench as usual; the command-line tool then reads it as the workbench left it.

  • Settings come from the project. It reads the schema files and settings from the project's hidden settings files, and the builders enabled on each profile's Profile Summary tab from the profile itself. CIMTool creates these files when a project is created, opened or imported.
  • Your preferences travel with the project. The project also keeps a copy of your CIMTool preferences, including the PlantUML Builder Preferences, in a hidden .cimtool-global-preferences file. CIMTool keeps it up to date when it starts, when a project is opened or imported, and when you apply changes on those preference pages. With it, the command line produces the same output as the workbench, even on a computer where CIMTool has never been installed.
  • Copyright templates are used automatically. If the project has copyright templates, the generated artifacts carry them, as they do in the workbench.

Keep these hidden files with the project when you commit it to a repository; see Hidden Files.

What It Generates

  • By default it processes every profile in the project's Profiles folder, running the builders enabled on each profile, and writes the artifacts to the Profiles folder beside the profiles, exactly as the workbench does.
  • It can process a single profile, run one named builder instead of the ones enabled on the profiles, or write the artifacts to another folder.
  • It includes every builder bundled with CIMTool, including the Java-based builders for OWL, RDFS, Turtle and XML that used to run only in the workbench. It can also run your own XSLT stylesheet as a custom builder.
  • It reports success or the kind of failure through its exit code, so a pipeline can stop when generation fails.

Getting and Running It

cimtool-cli.jar is an optional download, published with each CIMTool release since 2.3.0 on the CIMTool GitHub Releases page, separately from the CIMTool application. It needs Java 17 or later and nothing else. For example, to generate all of a project's artifacts:

java -jar cimtool-cli.jar --project-dir MyProject

Use the cimtool-cli release that matches the CIMTool release the project was last opened with. The command-line tool relies on the settings that CIMTool writes into the project, such as the hidden .cimtool-settings and .builder-preferences files. A newer cimtool-cli may need settings that an older CIMTool never wrote, and an older one may not understand settings or builders added by a newer CIMTool. A different release may still work, depending on what changed between the two releases, but if it does not, generation can fail or, worse, produce artifacts that differ from the workbench's without any error. Using the same release is always the safest choice, and is the recommended practice. When you upgrade CIMTool, open each project in the new release and commit the project's files, and upgrade the cimtool-cli.jar your pipelines use at the same time.
