
== **CIMToolPlugin**

The core Eclipse RCP plugin for the CIMTool application. It provides all of the
user-facing Eclipse UI, perspectives, editors, views, wizards, actions, and the
incremental build system, that together constitute the CIMTool workbench
experience.

This is the largest and most central of the in-repository plugins. All user
interaction with CIMTool at the GUI level flows through this plugin.



=== Overview

CIMToolPlugin (`au.com.langdale.cimtoole`) is the Eclipse plugin activator and
primary UI contributor for CIMTool. It integrates with the Eclipse IDE framework
to provide:

* The *CIMTool Perspective* and the *CIMTool Browsing* and *Validation* perspectives
* Editors for CIM profiles, model artefacts, mappings, diagnosis output, and repair files
* Wizards to create CIMTool projects, profiles, rulesets and mappings, and to
  import schemas (Sparx EA `.eap`, `.eapx`, `.qea`, `.qeax` project files and
  `.xmi` files), profiles, spreadsheets, rules, copyright templates, XSLT
  transform builders, CIM/XML models and existing CIMTool projects
* An incremental *CIMBuilder* that runs automatically on workspace resource changes
  and produces all configured output artefacts from a CIM profile
* Views for project models, documentation, validation results, and the PlantUML
  Real-Time Preview of the active profile
* Preference and property pages for general settings and PlantUML builder
  configuration, at workspace, project and file level
* Extension point registries for pluggable model parsers and profile buildlets
* An embedded Pandoc distribution, extracted at startup and held for possible
  future use; no CIMTool feature currently invokes it
* A unified logging pipeline that installs the JUL-to-SLF4J bridge at startup and
  extracts `logging.properties` and `logback.xml` so all three logging subsystems
  (JUL, SLF4J, Log4j 1.x) converge into a single Logback-controlled output in
  `logs/cimtool.log`

=== Plugin Activator: CIMToolPlugin.java

The bundle activator (`CIMToolPlugin.java`) runs when the plugin is first
activated and is responsible for:

. *`configureLogging()`*: First calls `SLF4JBridgeHandler.removeHandlersForRootLogger()`
  to remove any existing JUL handlers from the root logger, preventing duplicate
  log output. Then installs `SLF4JBridgeHandler` to redirect all JUL events into
  the SLF4J -> Logback pipeline, giving CIMTool a single unified log output in
  `logs/cimtool.log`. Filters `System.err` via an `AtomicBoolean`-guarded
  `PrintStream` to suppress the multi-line UCanAccess reserved-word warning, which
  originates from a direct `System.err.println` call inside the JDBC driver and
  cannot be suppressed via logging configuration. In production mode
  (`!Platform.inDevelopmentMode()`) additionally redirects `System.out` and
  `System.err` through JUL loggers `CIMTool.console.out` (INFO) and
  `CIMTool.console.err` (WARNING) so all console output is also captured in
  `logs/cimtool.log` via the bridge. In development mode the streams are left
  untouched so output remains visible in the Eclipse Console view.

. *`extractLoggingProperties()`*: On first run, extracts both
  `logging.properties` and `logback.xml` from the
  `au.com.langdale.cimtool.product` plugin bundle to the installation root
  directory, and creates the `logs/` subdirectory. On subsequent runs both files
  are already present and are loaded by the JVM and Logback respectively via the
  `-Djava.util.logging.config.file` and `-Dlogback.configurationFile` JVM
  arguments set in `CIMTool.ini`.

. *`loadEmbeddedPandocLibraries()`*: On first run, extracts the platform-specific
  Pandoc binary ZIP from the `native/` directory of this bundle to the Eclipse
  state location (`~/.cimtool-workspace/.metadata/.plugins/au.com.langdale.cimtoole/native/<platform>/pandoc/`).
  On subsequent runs the already-extracted binary is used directly.

. Installs the CIMTool icon cache, then initialises the shared *`Cache`*,
  *`Settings`*, *`BuilderPreferences`*, and *`GlobalPreferencesSynchronizer`* singletons that the rest of the plugin
  accesses via static getters.

==== Development vs Production Mode

`Platform.inDevelopmentMode()` returns `true` when CIMTool is launched from an
Eclipse Run Configuration (i.e. the developer's IDE), and `false` when running
from an exported product. The activator uses this flag to gate stream redirection:
in development mode `System.out` and `System.err` are left untouched so all
output remains visible in the Eclipse Console view. The `System.err` UCanAccess
filter is always active regardless of mode. In production mode both streams are
redirected through JUL loggers `CIMTool.console.out` (INFO) and `CIMTool.console.err`
(WARNING), which are bridged to SLF4J by `SLF4JBridgeHandler` and captured in
`logs/cimtool.log` via Logback.



==== The Global Preferences File for the CLI

A project's `.cimtool-global-preferences` file mirrors the CIMTool preferences of
the workspace in use, so that `cimtool-cli`, which cannot read the Eclipse
preference store, uses the same customized defaults as the desktop application.
`GlobalPreferencesExporter` writes the file from the preference store, replacing
its contents only when they differ, so an up-to-date file is left untouched:

* when a CIMTool project is opened or imported, through the
  `GlobalPreferencesSynchronizer` resource change listener;
* when CIMTool starts, through the synchronizer's one-time startup scan, for every
  CIMTool project that is already open, since such projects raise no open event;
* when changes are applied on the *CIMTool* and *PlantUML Builder Preferences*
  preference pages, for every open CIMTool project.

Project-level and profile-level settings made on a project's *Properties* pages
are stored in `.builder-preferences` and take precedence over the file, in the
desktop builders and in `cimtool-cli` alike.



[[preferences-and-properties]]
=== Preferences and Properties

CIMTool settings are made at three levels:

[cols="1,3,3", options="header"]
|===
| Level | Where it is set | Where it is stored

| Workspace
| *Window > Preferences > CIMTool* (`GeneralPreferencesPage`) and its *PlantUML
  Builder Preferences* child page (`PlantUMLBuildersPreferencesPage`)
| The Eclipse preference store, with defaults set by `PreferenceInitializer`. It
  is exported to each project's `.cimtool-global-preferences` for `cimtool-cli`,
  as described above.

| Project
| *Properties > CIMTool* on the project (`PropertyPage`) and its *PlantUML
  Builder Preferences* child page (`PlantUMLBuilderPropertyPage`)
| Project settings, such as the merged schema file name, self-healing and the
  merging of shadow and mix-in extensions, in `.cimtool-settings` (`Settings`).
  PlantUML builder preferences, including the Profile Real-Time Preview Diagram
  Style, in `.builder-preferences` (`BuilderPreferences`).

| File
| *Properties > CIMTool* on a schema, instance or incremental file, and
  *Properties > PlantUML Builder Preferences* on a profile (`.owl`) or a
  generated PlantUML file (`.puml`)
| Namespaces and the other file settings in `.cimtool-settings`; PlantUML
  builder preferences in `.builder-preferences`
|===

The *CIMTool* property page of a profile or `.puml` file is read-only. It shows
the file's location and points to where its settings are made.
`CIMToolPropertyTester` decides which resources show the *PlantUML Builder
Preferences* property page: CIMTool projects, profiles and generated `.puml`
files. The pages declare keywords, so the filter in the Preferences and
Properties dialogs finds them by the settings they hold, such as spacing, theme,
preview or mapping.

*Resolution.* A PlantUML builder preference resolves from the most specific
level that has a value of its own: the file's value, then its project's value,
then the workspace value (`Info.getBuilderPreference`). `cimtool-cli` resolves it
the same way from the project's files: `.builder-preferences` for the file and
project levels, then `.cimtool-global-preferences`, then the built-in default from
`CLIGlobalPreferenceDefaults` (`CLIBuilderPreferences`).

*Only genuine overrides are stored.* A project or file stores a builder
preference only when it differs from the value the resource would otherwise
inherit. Choosing the inherited value, or leaving the value empty, removes the
entry, so the resource keeps following later changes at a higher level
(`Info.setBuilderOverride`). Colors are compared without regard to case.

*Restore Defaults.* On a project or file page, Restore Defaults sets each
control to the value the resource inherits, so the following Apply removes that
page's overrides. On the workspace pages it restores the shipped defaults, as on
any Eclipse preference page.

*One save per Apply.* All the changes made by one Apply on a PlantUML Builder
Preferences property page are written to `.builder-preferences` in a single save
(`BuilderPreferences.runBatch`).

*Reading never writes.* Reading a setting that a resource does not hold
returns the inherited value without copying it into `.cimtool-settings`
(`Info.getProperty`). Values that must stay fixed for a resource, such as a
schema's namespace, are written when the resource is created or imported.

*Diagram Style from earlier releases.* Releases before 2.4.0 stored a
project's Diagram Style in `.cimtool-settings`. When a project's builder
preferences are loaded, `BuilderPreferences` moves such a value into
`.builder-preferences`, keeping any value already there and dropping an empty
one, and removes it from `.cimtool-settings`.



=== Incremental Build System

The `builder/` package implements CIMTool's incremental build system, which
integrates with the Eclipse *workspace build* mechanism:

* `CIMBuilder`: the Eclipse `IncrementalProjectBuilder` implementation.
  Registered via `org.eclipse.core.resources.builders` in `plugin.xml`.
  Determines which resources have changed and dispatches to the appropriate
  buildlets.

* `Buildlet`: abstract base class for all build steps. Each buildlet is
  responsible for one output artefact type.

* `ProfileBuildlets`: orchestrates the full set of buildlets for a profile
  build, including consistency checks, all registered transform builders, and
  report generation.

* `ConsistencyChecks`: validates the profile against the background model
  before building.

* `ValidationBuildlet` / `IncrementalValidationBuildlet` / `SplitValidationBuildlet`:
  buildlets for the various validation output modes.

* `ValidationBaseBuildlet`: shared base class for the validation buildlets.

* `SchemaBuildlet`: handles schema-related build steps.

* `PlantUMLRealTimePreviewBuildlet`: generates a hidden dot-prefixed `.puml` file
  in the `Profiles/` folder on every `.owl` profile save, triggering the Real-Time
  Preview pipeline. See the <<plantuml-real-time-preview,PlantUML Real-Time Preview>>
  section below.

* `UpgradeRegeneration`: records which CIMTool version last regenerated each
  project's artifacts and regenerates them once after an upgrade. See
  <<regeneration-after-an-upgrade,Regeneration After an Upgrade>> below.

* `UpgradeRegenerationStartup`: the startup class and resource change listener
  that queue projects for `UpgradeRegeneration`.

The build is triggered automatically by Eclipse whenever a relevant workspace
resource changes (a profile, model, or settings file). It can also be triggered
manually via *Project > Build Project*.

[[regeneration-after-an-upgrade]]
==== Regeneration After an Upgrade

`CIMBuilder` rebuilds only the outputs of resources that change, so a newer
CIMTool release opening a workspace built by an earlier one would otherwise leave
every generated artifact as the earlier builders produced it. CIMTool therefore
regenerates each project's profile artifacts once, the first time the project is
opened by a newer release.

*The stamp.* Each project carries an Eclipse persistent property,
`au.com.langdale.cimtoole:lastFullBuildVersion`, holding the CIMTool version
(major.minor.micro, for example `2.3.1`) that last regenerated all of its
artifacts. Persistent properties live in the workspace's `.metadata`, not in the
project folder, so the stamp never appears in Git and never travels with the
project. It is intentionally not stored in `.cimtool-settings`, which is the
project's portable configuration shared through Git and read by `cimtool-cli`: a
stamp written there by one workspace would suppress regeneration in another
workspace that never built the project. For the same reason, the property key is
defined in `UpgradeRegeneration` rather than in `QualifiedNames`, whose constants
`Settings` maps into `.cimtool-settings`.

*The version.* The running version is the `Bundle-Version` of CIMUtil
(`au.com.langdale.cimutil`), which holds the builders, `ProfileSerializer`, and
the post-processing stylesheets, reduced to major.minor.micro so that the build
qualifier is ignored. Versions compare numerically as
`org.osgi.framework.Version`, so 2.10.0 is newer than 2.9.0, and a version
written with fewer components is completed with zeros, so 2.4 equals 2.4.0.

*When the stamp is written.*

* `CIMBuilder` writes it after a build that traversed the whole project (a full
  build, a first build with no prior build state, or a rebuild triggered by a
  schema change) and completed without an exception. Incremental builds leave it
  unchanged.
* Regeneration writes it after regenerating a project.
* `Task.createProject` writes it when a project is created, since a project
  created by the running release has no artifacts from an earlier one.

*When a project is regenerated.* A project is regenerated when it is open, has
the CIMTool nature, and its stamp is missing or older than the running version
(`UpgradeRegeneration.needsUpgradeRebuild`). A stamp equal to or newer than the
running version never triggers regeneration, so opening a workspace with an older
CIMTool does nothing.

*What is regenerated.* Only the profile artifacts: every `ProfileBuildlet`
returned by `CIMBuilder`, run through the same worker as a build. Each output is
built when its builder is enabled on the profile and removed otherwise, exactly as
a full build does. The schema and instance validation are not rebuilt.

*Triggers.* All three queue projects through `UpgradeRegeneration.schedule`:

[cols="2,3", options="header"]
|===
| Trigger | Covers

| `UpgradeRegenerationStartup.earlyStartup()`
| Every open project when CIMTool starts, which covers a new release launched
  against an existing workspace

| The resource change listener registered by `earlyStartup()`
| Projects added to the workspace or opened later, for example by a generic
  Eclipse import or by opening a closed project

| The Import CIMTool Projects wizard
| The projects it imports, so that they are covered even when startup
  contributions are disabled under *Window > Preferences > General > Startup and
  Shutdown*
|===

Queued projects are regenerated by a single background job ("Regenerating CIMTool
artifacts after upgrade to X.Y.Z"). The job first waits for any automatic build in
progress, since the first build of a newly imported project already stamps it, and
then re-checks each project's stamp under the workspace build rule, skipping those
already current. It runs whether or not *Build Automatically* is enabled, and
writes one INFO entry per regenerated project to the Error Log.

NOTE: Because the running version comes from CIMUtil's `Bundle-Version`, a release
that does not bump it never triggers regeneration in upgraded workspaces.
`ReleaseVersionConsistencyTest` in CIMUtilTest fails when the product-aligned
versions disagree.



=== Pandoc Integration

Pandoc is bundled in anticipation of possible future use. No CIMTool feature
currently invokes it, and whether to keep it or remove it is still to be decided.

Pandoc is embedded as platform-specific ZIP archives in the `native/` directory
and extracted on first run by `CIMToolPlugin.loadEmbeddedPandocLibraries()`.
The current bundled version is documented in `native/README.TXT`. Extraction is
implemented for Windows and macOS. A Linux archive is bundled ahead of Linux
support, which is tracked in
https://github.com/cimug-org/CIMTool/issues/325[Issue #325].

The `pandoc/` package holds the supporting classes:

* `PandocPathResolver`: resolves the path to the Pandoc executable within the
  extraction directory: `pandoc.exe` on Windows, and `bin/pandoc` on macOS and
  Linux.

* `PandocConverter`: runs the Pandoc executable as a subprocess to convert a
  file from one format to another. No code calls it at present.

=== PlantUML Real-Time Preview

The Real-Time Preview feature renders a live PlantUML class diagram of the active
CIM profile in the `CurrentProfilePlantUmlSvgView` view. The pipeline has three
components:

* *`PlantUMLRealTimePreviewBuildlet`*: a `TextBuildlet` registered in `CIMBuilder`
  that fires on every `.owl` profile save. It generates a hidden dot-prefixed `.puml`
  file (e.g. `.EndDeviceConfig.puml`) in the project's `Profiles/` folder. The
  dot-prefix keeps the file out of CIMTool's resource model and prevents it from
  appearing in the user's workspace as a build artefact.

* *`CurrentProfilePlantUmlSvgView`*: a `ViewPart` that tracks the active profile
  editor via `IPartListener2` and the generated `.puml` file via
  `IResourceChangeListener`. When either changes, it invokes the PlantUML library
  (`net.sourceforge.plantuml.library`) with `PLANTUML_SECURITY_PROFILE=SANDBOX`
  to render the `.puml` to SVG, then injects the SVG into the embedded `Browser`
  widget using in-place DOM replacement via `BrowserFunction` + `DOMParser` to
  avoid visual flash-of-content artifacts.

* *`svg-pan-zoom.js`* (`js/svg-pan-zoom.js`), the pan/zoom library bundled locally
  and injected into the Browser widget. Bundled locally rather than loaded from a
  CDN to ensure air-gap compliance in utility company environments with no internet
  access.

Diagram style (the XSLT builder used to generate the `.puml`) is configurable via
a three-tier preference hierarchy: profile-level -> project-level -> global. Global
defaults are set in `PlantUMLBuildersPreferencesPage`. The profile and project
levels are stored in `.builder-preferences`, as described in
<<preferences-and-properties,Preferences and Properties>>.

`net.sourceforge.plantuml.library` is a hard `Require-Bundle` dependency, since
the preview pipeline calls the PlantUML API directly. `net.sourceforge.plantuml.eclipse`
is also a hard `Require-Bundle` dependency, because the CIMTool perspective places
its PlantUML Svg view, but the preview pipeline does not use it.



=== Relationship to Other Projects

* *CIMUtil*: CIMToolPlugin is the Eclipse UI shell around CIMUtil's core logic.
  The build system in `builder/` delegates all model parsing, profile processing,
  and artefact generation to classes in CIMUtil. CIMToolPlugin never duplicates
  this logic.

* *Kena*: the RDF graph used by the `Cache` and the editors is the Kena
  `OntModel` API. CIMToolPlugin never calls Apache Jena directly.

* *RCPUtil*: all custom Eclipse UI infrastructure (form binding, wizard base
  classes, JFace plumbing) comes from RCPUtil. CIMToolPlugin's editors and
  wizards extend RCPUtil base classes rather than raw Eclipse classes.

* *CIMToolProduct*: the product project that packages CIMToolPlugin into a
  runnable application. `CIMToolPlugin.java` references the product bundle
  (`au.com.langdale.cimtool.product`) by its symbolic name when extracting
  `logging.properties` and `logback.xml` at startup.

* *com.cimphony.cimtoole*: contributes to both extension points that
  CIMToolPlugin defines, registering Ecore model parsers through `model_parser`
  and the Ecore buildlet through `profile_buildlet`.

* *CIMToolTest*: a fragment of CIMToolPlugin that tests it as JUnit Plug-in
  Tests.

* *cimtool-cli*: the CLI project sources `cimutil.jar` from the PDE export of
  this plugin's sibling projects. CIMToolPlugin itself is not used at runtime by
  the CLI, but the same underlying CIMUtil logic is what the CLI invokes
  headlessly.
